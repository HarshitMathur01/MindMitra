## 1. System Overview

MindMitra's memory system gives the AI companion **persistent, cross-session memory** so it can remember user facts, coping strategies, emotional patterns, and synthesized insights across conversations. The system is inspired by three academic papers:

- **Stanford Generative Agents** (Park et al., 2023) — composite scoring with recency × importance × relevance
- **MemGPT** (Packer et al., 2023) — tiered memory with reflections
- **CoALA Framework** (Weng, 2023) — semantic / procedural / episodic taxonomy

### Architecture at a glance

```
User message arrives
    │
    ▼
┌──────────────────────────────────────────────────────────────┐
│  RETRIEVAL (synchronous, before response generation)         │
│                                                              │
│  1. mem0.search(query, user_id, limit=25)  ← over-fetch     │
│  2. Supabase: fetch metadata (importance, last_accessed_at)  │
│  3. Compute composite score per memory                       │
│  4. Bucket into semantic / procedural / reflection           │
│  5. Apply intent-based limits (casual=3…therapeutic=7)       │
│  6. Format as structured context string                      │
│  7. Append emotional trend (cached, 1hr TTL)                 │
│  8. Inject into ResponseGenerator system prompt              │
│                                                              │
│  Total: 0 LLM calls (pure scoring + DB lookups)              │
└──────────────────────────────────────────────────────────────┘
    │
    ▼
  Response generated by GLM
    │
    ▼
┌──────────────────────────────────────────────────────────────┐
│  STORAGE (asynchronous, background threads after response)   │
│                                                              │
│  Every 12 messages:                                          │
│    1. Fetch last 12 messages from Supabase                   │
│    2. mem0.add(messages) → Groq llama-3.3-70b extracts facts │
│    3. all-MiniLM-L6-v2 embeds → Qdrant upsert (384-dim)     │
│    4. Groq: batch importance scoring (1-10)                  │
│    5. Supabase: upsert memory_metadata                       │
│    6. Supabase: update user_memory_stats                     │
│                                                              │
│  Every 36 messages (3 × 12):                                 │
│    7. Gemini: generate session summary → session_summaries   │
│    8. Procedural synthesis (if coping keywords detected)     │
│    9. Reflection generation (every 5th session)              │
│   10. PHQ-9/GAD-7 screening with EMA smoothing               │
│                                                              │
│  Total: 2-4 LLM calls (all background, non-blocking)        │
└──────────────────────────────────────────────────────────────┘
```

## 3. Memory Types & Taxonomy

The system maintains four memory types, inspired by the CoALA cognitive architecture:

| Type | Description | Default Importance | Created By | Storage |
|---|---|---|---|---|
| **`semantic`** | Facts about the user — name, relationships, preferences, experiences | LLM-scored (1-10) | `mem0.add()` fact extraction | Qdrant + `memory_metadata` |
| **`procedural`** | Coping strategies & therapeutic techniques that work for this user | Minimum 8 (floor) | `synthesize_procedural_memory()` at session end | Qdrant + `memory_metadata` |
| **`reflection`** | High-level cross-session insights synthesized from accumulated memories | Fixed 9 | `generate_reflections()` every 5 sessions | Qdrant + `memory_metadata` |
| **`crisis`** | Crisis-related information — triggers, safety plans, crisis history | Fixed 10 | `add_crisis_memory()` from crisis fast-path | Qdrant + `memory_metadata` |

### How types are determined

- **At extraction time**: `add_memories()` receives a `metadata.category` field. If `category == "procedural"` → `procedural`. If `category == "crisis"` → `crisis`. Otherwise → `semantic`.
- **At retrieval time**: Each memory's type is looked up from `memory_metadata.memory_type` in Supabase.
- **Reflections**: Always stored with `category="reflection"` and `memory_type="reflection"`.

### Importance score overrides by type

```python
# In _score_and_save_metadata():
if memory_type == "crisis":
    scores = [10] * len(scores)           # Crisis memories always maximum importance
elif memory_type == "procedural":
    scores = [max(8, s) for s in scores]  # Procedural memories minimum 8
# semantic: uses actual LLM-scored value (1-10)
```

## 4. MemoryManager Singleton — Lifecycle

`MemoryManager` is instantiated as a **module-level singleton** at the bottom of `memory_manager.py`:

```python
# At module import time:
memory_manager = MemoryManager()
```

This means the singleton is created when `memory_manager.py` is first imported (typically during `workflow.py` import at server startup). The `__init__` method:

1. Sets all instance variables to `None` / empty
2. Creates a `threading.Lock` for init synchronization
3. Creates an in-memory emotional trend cache (`Dict[str, Tuple[str, float]]`)
4. Spawns a **daemon background thread** (`name="mem0-init"`) calling `_deferred_init()`

**Why deferred?** Loading the `sentence-transformers/all-MiniLM-L6-v2` model takes 2-5 seconds. If this blocked the main thread, FastAPI couldn't respond to Railway's health check within the 40-second timeout. The deferred init ensures the server starts immediately.

### Instance variables

```python
self._mem0          # mem0.Memory instance (or None if init failed)
self._ready         # bool: True only after successful mem0 init
self._gemini_model  # google.generativeai.GenerativeModel (for session summaries)
self._glm           # GLMController instance (for procedural synthesis)
self._groq_client   # groq.Groq instance (for importance scoring, reflections, trend)
self._init_lock     # threading.Lock (guards deferred init)

self._emotional_trend_cache                # Dict[user_id → (trend_text, monotonic_timestamp)]
self._EMOTIONAL_TREND_CACHE_TTL_S = 3600.0 # 1 hour cache TTL
```

4. Sets `self._ready = True` on success

```python
genai.configure(api_key=GOOGLE_API_KEY)
```

Used exclusively for session summaries.

### 5.3 GLM Controller


Used for procedural memory synthesis (extracting coping strategies).

### 5.4 Groq Client

```python
from groq import Groq
self._groq_client = Groq(api_key=GROQ_API_KEY)
```

Used for importance scoring, reflection generation, and emotional trend analysis.

## 6. Memory Storage Pipeline

### Trigger

Memory extraction is triggered by `_maybe_trigger_memory()` in `chat.py`:

```python
def _maybe_trigger_memory(session_id, user_id):
    session_message_counters[session_id] += 1
    count = get_hybrid_message_count(session_id)  # max(db_count, in_memory_count)
    if count > 0 and count % MEMORY_TRIGGER_INTERVAL == 0:  # every 12 messages
        messages = fetch_last_n_messages(session_id, n=MEMORY_TRIGGER_INTERVAL)
        # Fire and forget in background thread:
        threading.Thread(target=memory_manager.add_memories, args=(messages, user_id, session_id), daemon=True).start()
```

### `add_memories()` — Step by step

1. **Guard**: Return early if `self._ready` is False or `self._mem0` is None
2. **Prepare metadata**: Copy caller's metadata, add `session_id` and default `source: "conversation"`
3. **Call `self._mem0.add()`**:
   - mem0 internally calls Groq `llama-3.3-70b-versatile` to extract atomic facts from the messages
   - Each fact is embedded by `all-MiniLM-L6-v2` into a 384-dim vector
   - Vectors are upserted into Qdrant collection `companion_memories`
   - mem0 handles deduplication (if a similar fact already exists, it updates rather than duplicates)
4. **Determine memory type**: Based on `metadata.category` — `"procedural"` → procedural, `"crisis"` → crisis, else → semantic
5. **Spawn background thread** for `_score_and_save_metadata()` (importance scoring + Supabase metadata)
6. **Return** the mem0 result dict

### Data flow diagram

```
User + AI messages (last 12)
    │
    ▼
mem0.add(messages, user_id, metadata)
    │
    ├─ [Internal] Groq llama-3.3-70b: extract atomic facts
    │     "User's name is Harshit"
    │     "User is stressed about JEE preparation"
    │     "User finds breathing exercises helpful"
    │
    ├─ [Internal] all-MiniLM-L6-v2: embed each fact → 384-dim vector
    │
    ├─ [Internal] Qdrant: upsert vectors with mem0 IDs
    │
    └─ Returns: { "results": [ { "id": "mem0-uuid", "event": "ADD", "memory": "..." }, ... ] }
         │
         ▼
    _score_and_save_metadata() [background thread]
         │
         ├─ Filter: only results with event == "ADD"
         ├─ Extract text: [m["memory"] for m in new_memories]
         ├─ Groq: _score_importance_batch(texts) → [5, 7, 3, ...]
         ├─ Apply type overrides (crisis=10, procedural≥8)
         ├─ Supabase: INSERT INTO memory_metadata
         │     (user_id, mem0_id, category, importance, importance_score,
         │      memory_type, last_accessed_at, source)
         └─ Supabase: UPSERT INTO user_memory_stats
               (user_id, total_memories, last_extraction, session_count)
```

## 7. Importance Scoring

Importance scoring assigns each extracted memory a value from 1-10, following the Generative Agents paper. This score determines how prominently a memory appears in future retrievals.

### `_score_importance_batch(memory_texts)`

**Input**: List of memory text strings  
**Output**: List of integers (1-10)  
**LLM**: Groq `llama-3.3-70b-versatile`, temperature=0.1, max_tokens=200

**Prompt structure**:
```
Rate the personal importance of each memory on a 1-10 scale
for a companion AI that wants to deeply understand this person.

Scale:
1-2 = trivial daily details (e.g., 'user said hi')
3-4 = minor preferences or routine facts
5-6 = notable preferences, habits, or social context
7-8 = significant life events, emotional struggles, or relationships
9-10 = crisis, trauma, core identity, or deeply personal revelations

Memories:
1. User's favorite color is blue
2. User was bullied in school and still has trust issues

Return ONLY a JSON array of integers, e.g. [3, 8]. No other text.
```

**Fallback**: If Groq fails or returns unexpected format, all memories get default score of **5**.

### Score-to-label mapping

```python
score >= 9  → "critical"
score >= 7  → "high"
score >= 4  → "medium"
score < 4   → "low"
```

The label is stored in `memory_metadata.importance` (string column), while the raw score goes in `memory_metadata.importance_score` (integer column).

## 8. Composite Retrieval Scoring

When retrieving memories for a user message, the system computes a **composite score** for each candidate memory using three factors:

### Formula

$$\text{score} = \alpha_v \cdot \text{relevance} + \alpha_i \cdot \text{importance} + \alpha_r \cdot \text{recency}$$

Where:
- $\alpha_v = 0.50$ (relevance weight) — from `SCORE_WEIGHT_RELEVANCE`
- $\alpha_i = 0.35$ (importance weight) — from `SCORE_WEIGHT_IMPORTANCE`
- $\alpha_r = 0.15$ (recency weight) — from `SCORE_WEIGHT_RECENCY`

### Factor computation

| Factor | Source | Formula | Range |
|---|---|---|---|
| **relevance** | mem0 similarity score (cosine similarity from Qdrant ANN search) | Direct from `m["score"]` | 0.0 – 1.0 |
| **importance** | `memory_metadata.importance_score` from Supabase | `importance_score / 10.0` | 0.0 – 1.0 |
| **recency** | `memory_metadata.last_accessed_at` from Supabase | $0.999^{\text{hours\_since\_last\_access}}$ | 0.0 – 1.0 |

### Recency decay curve

The recency factor uses **exponential decay** with rate `RECENCY_DECAY_RATE = 0.999`:

```python
recency = 0.999 ** hours_elapsed
```

| Time since access | Recency score |
|---|---|
| 0 hours | 1.000 |
| 24 hours (1 day) | 0.976 |
| 168 hours (1 week) | 0.845 |
| 720 hours (1 month) | 0.487 |
| 2160 hours (3 months) | 0.115 |

This means memories accessed recently get a small boost, but the decay is gentle enough that old important memories still surface.

### Retrieval flow — step by step

```python
def retrieve_memories(query, user_id, intent="emotional", limit=5, threshold=0.3):
```

1. **Over-fetch**: `mem0.search(query, user_id, limit=25)` — fetches 25 candidates from Qdrant
2. **Fetch metadata**: `_fetch_metadata_for_scoring(user_id)` — single Supabase query for all user's metadata rows
3. **Score each memory**:
   - Look up `importance_score` and `last_accessed_at` from metadata map
   - Default importance = 5 if not found
   - Default hours_elapsed = 0 if no `last_accessed_at`
   - Compute composite score
4. **Sort** by composite score (descending)
5. **Bucket** into semantic, procedural, reflection lists
6. **Apply intent limits**: `semantic_memories` capped at intent limit; procedural capped at 2 for non-therapeutic; reflections capped at `REFLECTION_MAX_INSIGHTS` (5)
7. **Filter**: Skip any memory below `MEMORY_RELEVANCE_THRESHOLD` (0.25)
8. **Update access timestamps** (background thread)
9. **Format** as structured context string

## 9. Intent-Based Retrieval Limits

The number of semantic memories returned depends on the classified intent of the user's message:

| Intent | Max Semantic Memories | Rationale |
|---|---|---|
| `casual` | 3 | Light conversation — minimal memory needed |
| `emotional` | 5 | Moderate — need enough context for empathy |
| `therapeutic` | 7 | Deep — need comprehensive user understanding |
| `crisis` | 4 | Focused — need crisis-relevant memories quickly |

**Constants** (from `constants.py`):
```python
MEMORY_LIMIT_CASUAL = 3
MEMORY_LIMIT_EMOTIONAL = 5
MEMORY_LIMIT_THERAPEUTIC = 7
MEMORY_LIMIT_CRISIS = 4
```

**Procedural memories** are handled separately:
- For `therapeutic` and `crisis` intents: all retrieved procedural memories are included (no cap)
- For `casual` and `emotional` intents: capped at 2

**Reflection memories**: Always capped at `REFLECTION_MAX_INSIGHTS` (5).

## 10. Structured Memory Formatting

Retrieved memories are formatted into a structured string with labeled sections before injection into the ResponseGenerator's system prompt:

### Format

```
🧠 WHAT YOU KNOW ABOUT THIS USER:
• User's name is Harshit and he's a 3rd year engineering student (score: 0.78)
• User has anxiety about JEE Advanced preparation (score: 0.72)
• User's parents put a lot of academic pressure on him (score: 0.65)

💡 COPING STRATEGIES THAT WORK FOR THEM:
• Practice 4-7-8 breathing technique when anxiety peaks, especially before exams
• Going for evening walks helps clear the mind when feeling overwhelmed

🔮 YOUR UNDERSTANDING OF THIS USER:
• This person shows a recurring pattern of seeking validation from authority figures
• They tend to internalize academic failure as personal inadequacy

📈 EMOTIONAL TREND (recent sessions): User has shown gradually decreasing anxiety
but persistent sadness about family expectations.
```

### Implementation

```python
def _format_structured_memory_context(semantic, procedural, reflections) -> str:
    sections = []
    if semantic:
        lines = ["🧠 WHAT YOU KNOW ABOUT THIS USER:"]
        for m in semantic:
            text = m.get("memory", "")
            score = m.get("composite_score", 0)
            lines.append(f"• {text} (score: {score:.2f})")
        sections.append("\n".join(lines))
    # ... similar for procedural and reflections
    return "\n\n".join(sections)
```

The emotional trend is appended separately by `_route_and_execute()` in `workflow.py`:
```python
trend = memory_manager.get_emotional_trend(user_id)
if trend:
    ctx["memory_context"] += f"\n\n📈 EMOTIONAL TREND (recent sessions): {trend}"
```

## 11. Emotional Trend Analysis

Cross-session emotional continuity tracking synthesizes a one-sentence trend from recent session emotional arcs.

### `get_emotional_trend(user_id)`

**LLM**: Groq `llama-3.3-70b-versatile`, temperature=0.2, max_tokens=100

**Flow**:
1. **Cache check**: Look up `_emotional_trend_cache[user_id]` — if present and less than 1 hour old (`_EMOTIONAL_TREND_CACHE_TTL_S = 3600.0`), return cached value
2. **Fetch summaries**: `_fetch_recent_session_summaries_for_trend(user_id)` — last 5 sessions' `themes` and `emotional_arc` from `session_summaries` table
3. **Guard**: Need at least 2 sessions for a meaningful trend; return "" if fewer
4. **Build timeline**: Format each session as `"Session N: themes=[...], emotional_arc=[...]"`
5. **LLM call**: Ask Groq to write a single sentence describing the emotional trend
6. **Cache result**: Store `(trend_text, time.monotonic())` in cache
7. **Return** trend text

**Example output**:
```
User has shown gradually decreasing anxiety but persistent sadness about family relationships.
```

The trend is **not recomputed on every request** — it's cached for 1 hour per user, making it essentially free after the first call.

## 12. Session Summaries

### `save_session_summary(user_id, session_id, messages)`

**LLM**: Gemini `gemini-2.5-flash-lite`, temperature=0.3, max_output_tokens=500

**When triggered**: Every 36 messages (3 × `MEMORY_TRIGGER_INTERVAL`), via `_run_session_end_jobs()` in `chat.py`

**Prompt**: Asks Gemini to summarize the last 30 messages into:
```json
{
  "summary": "3-5 sentence summary",
  "themes": ["theme1", "theme2"],
  "emotional_arc": ["anxious", "validated", "hopeful"]
}
```

**Storage**: Upserted into `session_summaries` table with `on_conflict="session_id"`:
- `user_id`, `session_id`
- `summary_text` (string)
- `themes` (JSON string)
- `emotional_arc` (JSON string)
- `updated_at` (ISO timestamp)

### `load_session_summary(session_id)`

Simple SELECT from `session_summaries` for a given session. Returns `{summary, themes, emotional_arc}`.

### Cross-session continuity

`fetch_previous_session_summary()` in `supabase_service.py` fetches the most recent session summary that is NOT the current session. This is loaded in `chat.py` and passed to `process_chat()` as `previous_session_summary`, which becomes available in the ResponseGenerator's context as:

```
PREVIOUS SESSION CONTEXT:
  Summary: User discussed anxiety about upcoming exams...
  Key themes: ["academic stress", "self-doubt"]
  Emotional journey: ["anxious", "frustrated", "slightly hopeful"]
  Reference this naturally if it connects to what they're sharing now — it shows you remember.
```

## 14. Reflection Generation

Reflections are higher-level insights synthesized from accumulated memories and session histories. They represent the companion's evolving understanding of the user.

### Trigger

```python
def should_generate_reflections(user_id) -> bool:
    stats = self.get_user_memory_stats(user_id)
    session_count = stats.get("session_count", 0)
    return session_count > 0 and session_count % REFLECTION_INTERVAL_SESSIONS == 0
    # REFLECTION_INTERVAL_SESSIONS = 5
```

Checked during `_run_session_end_jobs()` — if True, spawns a background thread.

### `generate_reflections(user_id)`

**LLM**: Groq `llama-3.3-70b-versatile`, temperature=0.3, max_tokens=600

**Steps**:

1. **Fetch top memories**: `_fetch_top_memories_for_reflection(user_id)` — gets top 30 memories by `importance_score` (excluding existing reflections) from `memory_metadata`, then loads actual text from mem0
2. **Guard**: Need at least 3 memories; return None if fewer
3. **Fetch all session summaries**: up to 20 most recent
4. **Build prompt**: Asks for 5 deep insights focusing on:
   - Recurring emotional patterns
   - Core values
   - Growth and positive changes
   - Unresolved struggles
   - What makes them feel safe and connected
   - Relationship dynamics and family patterns
5. **LLM call**: Returns JSON array of 5 insight strings
6. **Store each reflection**: Via `mem0.add()` with `category="reflection"`, `source="reflection_synthesis"`, `importance="critical"`
7. **Save metadata**: For each reflection, search mem0 to find the matching ID (score > 0.9), then insert into `memory_metadata` with `importance_score=9`, `memory_type="reflection"`

**Example reflections**:
```json
[
  "This person shows a recurring pattern of seeking validation from authority figures, likely rooted in family dynamics where academic achievement was the primary measure of worth.",
  "They tend to internalize academic failure as personal inadequacy, but have recently started to question this pattern.",
  "A recurring theme is the conflict between their own interests and parental expectations — they're slowly developing the language to express this tension.",
  "Physical exercise, especially walking, consistently appears as their most effective coping mechanism across sessions.",
  "There's a growing sense of self-awareness: they're becoming better at identifying their triggers and naming their emotions."
]
```

## 15. Crisis Memory Handling

### `add_crisis_memory(user_id, message, session_id)`

Called from `_crisis_fast_path()` in `workflow.py` when a crisis is detected. Stores the user's message as a critical memory:

```python
meta = {
    "importance": "critical",
    "category": "crisis",
    "source": "crisis_fast_path",
}
self._mem0.add(
    messages=[{"role": "user", "content": message}],
    user_id=user_id,
    metadata=meta,
)
```

Crisis memories always receive importance score 10 (maximum) and are stored with `memory_type="crisis"`.

At retrieval time, crisis memories are treated as semantic memories for bucketing purposes but their high importance score ensures they always appear near the top of composite-scored results.

## 17. Access Timestamp Tracking

Every time memories are retrieved and used, their `last_accessed_at` timestamps are updated in a background thread:

```python
def _update_access_timestamps(mem0_ids: List[str]):
    supabase_client.table("memory_metadata").update(
        {"last_accessed_at": now}
    ).in_("mem0_id", mem0_ids).execute()
```

This feeds back into the **recency** factor of the composite score. Frequently accessed memories maintain a higher recency score, creating a natural feedback loop where useful memories stay prominent.

## 19. Memory Trigger Mechanics

### Message counting

Two counting mechanisms work together:

1. **In-memory counter**: `session_message_counters[session_id]` — `defaultdict(int)` in `supabase_service.py`; incremented on every chat request
2. **Database counter**: `get_session_message_count(session_id)` — `SELECT COUNT(*) FROM chat_messages WHERE session_id = ?`

`get_hybrid_message_count()` returns `max(db_count, mem_count)` to handle cases where the DB count lags behind (messages saved from frontend asynchronously).

### Trigger intervals

| Interval | Action | Constant |
|---|---|---|
| Every 12 messages | Memory extraction (`add_memories`) | `MEMORY_TRIGGER_INTERVAL = 12` |
| Every 36 messages | Session-end jobs (summary + procedural + reflections + screening) | `MEMORY_TRIGGER_INTERVAL * 3` |

---

## 20. Session-End Jobs

`_run_session_end_jobs(session_id, user_id)` runs in a background thread every 36 messages:

```
1. Fetch last 30 messages
2. If ≥ 5 messages:
   a. Save session summary (Gemini → Supabase)
   b. Trigger procedural synthesis (if coping keywords detected)
   c. Check if reflections are due (every 5th session)
      → If yes, spawn reflection generation thread
3. If ≥ SCREENING_MIN_MESSAGES (8):
   d. Fetch previous screening scores
   e. Generate session-level PHQ-9/GAD-7 assessment
   f. Apply EMA smoothing with previous scores
   g. Save to Supabase
```

## 23. Error Handling Philosophy

Every public method in `MemoryManager` is wrapped in `try/except` with the following guarantees:

1. **A memory failure can NEVER crash the chat pipeline** — all errors are logged and the method returns a safe default (empty string, empty dict, False, None)
2. **All storage operations are fire-and-forget** — they run in background daemon threads, meaning the main request/response path is never blocked
3. **Each subsystem fails independently** — if Gemini is down, mem0 still works; if Qdrant is unreachable, the rest of the pipeline continues with empty memory context
4. **Degradation is graceful** — if no memories are available, the ResponseGenerator simply doesn't receive a `{memory_context}` block, and the response is generated without memory (like a first conversation)
